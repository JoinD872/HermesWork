# MXD 协作规则

> 适用范围：`E:\Opencode\MXD` 及其子目录
> 语言：能用中文表达的内容使用中文；文件名、函数名、命令和代码字段保留原文。

本文件规定 GPT、Codex、用户和 GitHub 在本项目中的协作方式。具体的安全边界、工具规则和目录规则，见各子目录的 `AGENTS.md` 与 `WORK_RULES.md`。

## 1. 角色分工

| 角色 | 负责内容 |
|------|----------|
| 用户 | 定义想要的效果，描述实际现象，提供运行反馈，完成最终验收 |
| GPT | 分析问题、提出方案、划定任务边界、制定验收标准、审查提交结果 |
| Codex | 读取真实代码、检查方案可行性、修改代码、运行测试、提交代码 |
| GitHub | 保存可追溯的代码版本、提交历史和协作记录 |
| 测试/日志/截图/录屏/实机 | 证明指定版本的实际行为 |

GPT 提出的方案是基于现有证据的建议，不是对代码结构的绝对指令。Codex 发现真实代码与方案不一致时，必须先说明差异，再按真实代码结构实现目标，不得机械修改已经不存在的代码。

## 2. 任务边界

每个需要修改代码或产出分析的任务，都必须先明确：

```text
【本轮目标】
【允许修改或产出】
【禁止修改或操作】
【验收标准】
【验证方式】
```

任务执行过程中不得无故扩大范围。发现必须扩大范围才能完成时，先说明原因、影响和新增文件，再继续；不得“顺便”重构无关模块。

## 3. 风险分级

不强制所有任务使用同一套仪式，按风险选择流程：

| 等级 | 典型任务 | 最低流程 |
|------|----------|----------|
| L0 | 文案、注释、单个显示字段 | 检查后直接修改并做基本验证 |
| L1 | 单文件普通问题 | 读取相关代码、修改、定向测试 |
| L2 | 状态机、导航、跨文件行为 | GPT 施工单、Codex 检查方案、实现、测试、提交、GPT 审查 |
| L3 | 核心架构、高风险安全边界、跨模块重构 | 独立分支或 PR、明确验证证据、GPT 审查后再合并 |

## 4. 三阶段完成状态

```text
实现完成 → 验证通过 → 用户验收
```

### 实现完成

必须同时具备：实际产出已经完成、修改或产出清单明确、有可追溯的提交号，并且没有混入任务外的已有修改。只修改但没有提交，不算实现完成。

### 验证通过

验证证据必须明确绑定：

1. 同一个提交号；
2. 对应的运行环境和配置；
3. 测试、日志、截图、录屏或实机证据；
4. 实际结果。

提交后又产生未提交修改时，后续结果不得直接证明之前的提交有效，除非明确证明运行的仍然是之前的提交版本。

### 用户验收

只有用户确认实际效果符合原始目标，才算最终完成。GPT 只能给出“建议验收”或“存在阻塞”，不得代替用户宣布实际效果已经验收。

## 5. 版本与工作区安全

- 开始任务前检查当前分支、提交号和工作区状态。
- 已有未提交修改时，不得擅自 `reset`、`stash`、覆盖、格式化或提交这些修改。
- 只提交本轮任务产生的文件；禁止使用无法确认范围的批量提交方式。
- 提交前检查差异是否只包含本轮任务。
- 所有验证结果都要记录其对应的提交号。
- 未经用户明确要求，不删除原始证据、历史分析或其他人的产出。

## 6. 文档职责

| 文件 | 职责 |
|------|------|
| `AGENTS.md` | 长期、稳定、必须遵守的协作和安全规则 |
| `WORK_RULES.md` | 当前目录的详细工作流程、工具和目录规范 |
| `CODEX_STATUS.md` | 当前项目状态、已验证版本、已知问题和待办 |
| `README.md` | 项目介绍、安装、运行和目录入口 |

`CODEX_STATUS.md` 是状态摘要，不替代代码、提交、测试和运行证据。
